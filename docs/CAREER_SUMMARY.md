## 2. 담당 업무 및 주요 성과

### 2-1. 13개 시즌 데이터를 4단계 드릴다운으로 좁히는 탐색 UI 설계

- 시즌 → 국가 → 리그 → 팀 → 경기 상세로 이어지는 4단계 탐색 구조를 설계하고, 각 단계를 Breadcrumb으로 되짚어 올라갈 수 있게 구성
- 상위 선택이 없으면 하위 쿼리가 아예 발화하지 않도록 React Query의 조건부 실행(`enabled`)을 적용
- **성과: 사용자가 국가를 고르기 전까지 리그·팀 API 요청이 발생하지 않는 구조로, 탐색 단계별 불필요 요청을 원천 차단**

### 2-2. 이미지 렌더링 최적화 (지연 로딩 + 썸네일 파이프라인 + 이미지 서버 분리)

- 팀 로고·선수 사진이 카드 리스트에 대량으로 깔리는 화면 특성상, 초기 렌더 비용이 이미지에 집중되는 구조를 개선
- `IntersectionObserver` 기반 지연 로딩 컴포넌트를 공통화하고, 뷰포트에 10%만 들어와도 로드되도록 임계값을 조정해 스크롤 중 빈 칸이 보이지 않게 처리
- 원본 이미지 URL에 규격 경로를 주입하는 유틸을 만들어 **로고 35px / 선수 사진 80px 썸네일 규격으로 전면 통일**, 이후 이미지 원천을 외부 API에서 **Azure Blob Storage 자체 이미지 서버로 이관**
- **성과: 초기 렌더 시점에 요청되는 이미지를 "뷰포트 안에 실제로 보이는 것"으로 한정하고, 표시 크기와 무관하게 원본을 내려받던 경로를 제거 — 화면 전체 이미지 요청 규격을 단일화**

### 2-3. 서버 상태 캐싱 전략 수립

- React Query를 도입해 서버 상태와 UI 상태를 분리하고, 목록·상세 화면 간 데이터 흐름을 재정의
- 변경 빈도가 낮은 팀 목록·경기 일정에 **10분 `staleTime`** 을 부여하고, `refetchOnWindowFocus`는 비활성화, 실패 재시도는 1회로 고정해 실패 시 지연이 누적되지 않게 조정
- 팀 상세 진입 시 목록에서 이미 받아둔 데이터를 **캐시에서 먼저 조회하고, 없을 때만 서버를 호출**하는 폴백 구조로 구현
- **성과: 목록 ↔ 상세를 오가는 가장 잦은 이동 경로에서 10분 캐시 윈도우 내 중복 요청 제거, 탭 복귀만으로 발생하던 재요청도 함께 제거**

### 2-4. 팀 로고 색상 기반 동적 테마 & 가독성 자동 보정

- 팀마다 브랜드 컬러가 다른데 팀별 색상을 수작업으로 정의하면 팀이 늘어날 때마다 유지보수가 따라붙는 문제를 인식
- `node-vibrant`로 로고에서 팔레트를 추출한 뒤 **픽셀 점유율이 가장 높은 색을 대표색으로 선택**, 그 위에 얹는 텍스트는 **YIQ 밝기 공식으로 계산해 임계값 140을 기준으로 흑/백을 자동 결정**
- **성과: 팀별 색상 정의를 코드에 하드코딩하지 않고도 모든 팀 상세 화면에서 배경-텍스트 대비를 자동 확보 — 신규 팀 추가 시 색상 관련 추가 작업 불필요**

### 2-5. iOS Safari 타임존 파싱 이슈 대응

- `"2024-08-18 15:30:00 UTC"` 형태의 서버 날짜 문자열이 iOS Safari에서 `Invalid Date`로 파싱되어, **동일 화면이 안드로이드에서는 정상, iOS에서는 경기 일정 정렬이 깨지는** 플랫폼 종속 버그 확인
- 파싱을 브라우저 구현에 맡기지 않고 ISO 8601로 정규화한 뒤 `date-fns-tz`로 KST 변환하는 공통 유틸로 일원화
- **성과: 브라우저별 날짜 파싱 편차 제거, 경기 일정 정렬·표기가 iOS/안드로이드/데스크톱에서 동일하게 동작**

### 2-6. 배포 자동화 (수동 3단계 → 무인 배포)

- 초기 배포는 `빌드 → tar 압축 → scp 전송`의 로컬 수동 3단계였고, 개인 키 경로가 npm 스크립트에 박혀 있어 배포 주체가 사실상 1인으로 고정되는 구조
- GitHub Actions에 **main 브랜치 push 트리거**로 빌드 → Docker 이미지 생성 → Docker Hub 푸시까지 이어지는 파이프라인을 구성하고, 멀티 스테이지 Dockerfile로 빌드 산출물만 런타임 이미지에 남기도록 분리
- **성과: 배포 시 사람이 수행하는 수동 단계 3 → 0, 배포 절차가 로컬 환경(키·OS·노드 버전)에 의존하지 않는 재현 가능한 형태로 전환**

## 4. 회고

### 회고 ① 이미지가 지배하는 화면의 초기 로딩

**문제인식**
카드 리스트 화면은 팀 로고와 선수 사진이 화면을 가득 채우는 구조라, 초기 렌더 비용의 대부분이 이미지에서 발생했다. 게다가 실제 표시 크기는 30~80px 수준인데 원본 이미지를 그대로 내려받고 있어, 화면에 보이지도 않는 아래쪽 카드까지 원본을 전부 받아오는 상태였다.

**방안수립**
1. Next.js `Image`의 기본 최적화에 위임
2. `IntersectionObserver`로 뷰포트 진입 시점에만 로드하는 지연 로딩 컴포넌트 직접 구현
3. 서버에서 규격별 썸네일을 미리 만들어 URL로 선택하는 이미지 파이프라인 구축

**방안선택 및 이유**
2 + 3을 함께 선택했다. 정적 export(`output: "export"`) 구성이라 Next.js의 런타임 이미지 최적화를 쓸 수 없었고, 최적화를 켜도 "표시 크기에 맞는 원본이 애초에 없다"는 문제는 그대로 남기 때문이다. 요청 시점 제어(지연 로딩)와 요청 크기 제어(썸네일)는 서로 다른 축의 문제라 판단해 둘 다 잡았고, 임계값은 10%로 두어 "스크롤이 도달하기 직전에 로드가 시작되도록" 타협했다.

**결과 및 성과**
초기 렌더 시 요청되는 이미지가 뷰포트 내부 항목으로 한정됐고, 이미지 요청 규격이 로고 35px / 선수 80px로 통일됐다. 이후 이미지 원천 자체를 Azure Blob Storage로 옮기면서 외부 API 응답 속도에 프론트 렌더가 묶이던 의존성도 끊었다.

**회고**
지연 로딩 전환 시 자리 표시자를 GIF 이미지로 둔 점은 아쉽다. 자리 표시자 자체가 네트워크 자원이라, CSS 스켈레톤이나 blur placeholder였다면 요청을 더 줄일 수 있었다. 또 이 작업의 효과를 개선 전후 전송량·LCP로 측정해두지 않아서 "구조적으로 좋아졌다"까지만 말할 수 있고 숫자로 증명하지 못한다. 이후 프로젝트에서는 최적화 착수 전에 기준선을 먼저 재는 것을 원칙으로 삼게 됐다.

### 회고 ② 화면을 오갈 때마다 반복되는 동일 요청

**문제인식**
목록에서 팀을 고르고 상세로 들어갔다가 뒤로 나오는 동선이 이 서비스의 가장 잦은 이동 경로인데, 매번 동일한 팀 목록을 다시 받아왔다. 시즌·국가·리그가 바뀌지 않았는데도 왕복마다 요청이 발생하는 구조였고, 데이터 원천이 배치로 갱신되는 성격이라 초 단위 최신성이 필요하지도 않았다.

**방안수립**
1. 전역 스토어(MobX)에 조회 결과를 직접 적재하고 수동으로 무효화
2. React Query 도입 후 쿼리 키 기반 캐싱에 위임
3. 상세 페이지에서 목록 데이터를 라우팅 상태로 넘겨 재요청 자체를 없애기

**방안선택 및 이유**
2를 축으로 하고 3의 발상을 캐시로 구현했다. 1은 로딩/에러/무효화 상태를 직접 관리해야 해서 화면이 늘수록 복잡도가 선형으로 증가하고, 3은 URL 직접 진입·새로고침 시 데이터가 비는 취약점이 있었다. 최종적으로 **상세 진입 시 캐시를 먼저 조회하고 없을 때만 서버를 호출**하는 폴백 구조로 두어, 일반 동선에서는 요청이 없고 URL 직접 진입에서도 화면이 정상 동작하도록 했다. 서버 상태는 React Query, 헤더 로고·스크롤 같은 순수 UI 상태는 MobX로 역할을 분리했다.

**결과 및 성과**
10분 캐시 윈도우 안에서 목록 ↔ 상세 왕복 시 중복 요청이 사라졌고, 탭 전환 복귀만으로 발생하던 재요청도 제거했다. 실패 재시도를 1회로 고정해 서버 지연 시 사용자가 체감하는 대기 시간이 누적되지 않게 했다.

**회고**
`staleTime` 10분은 "배치 주기보다 짧으면 된다"는 감각으로 정한 값이라, 실제 배치 갱신 주기와 정렬해 근거 있는 값으로 다시 정의했어야 했다. 또 로딩 처리를 화면 단위 전체 스피너로 둬서, 일부 쿼리만 늦어도 화면 전체가 멈춘 것처럼 보인다. 섹션 단위 로딩이나 스켈레톤으로 쪼갰다면 체감 속도가 더 좋았을 것이다.

### 회고 ③ 팀마다 다른 브랜드 컬러를 유지보수 없이 반영하기

**문제인식**
팀 상세 화면에 팀 고유의 색을 입히고 싶었지만, 팀 수만큼 색상을 정의하면 시즌·리그가 확장될 때마다 색상 정의가 따라 늘어나는 유지보수 부채가 된다. 반대로 자동 추출을 하면 어두운 로고에서 뽑힌 색 위에 검은 글씨가 얹히는 식으로 텍스트가 읽히지 않는 경우가 생긴다.

**방안수립**
1. 팀별 색상 상수 테이블을 만들어 관리
2. 백엔드에서 대표색을 계산해 응답에 포함
3. 클라이언트에서 로고 이미지를 분석해 대표색을 추출하고, 대비색도 함께 계산

**방안선택 및 이유**
3을 선택했다. 1은 확장할수록 부채가 커지고, 2는 색상 하나 때문에 API 스키마와 배치 로직을 건드려야 해서 변경 비용이 컸다. 대표색은 팔레트 중 **픽셀 점유율이 가장 높은 색**을 고르도록 해서 "화려하지만 로고에서 차지하는 비중은 작은 색"이 뽑히는 문제를 막았고, 텍스트 색은 취향이 아니라 **YIQ 밝기 계산 후 임계값 140** 으로 흑/백을 자동 결정하게 해 가독성을 규칙으로 보장했다. 색상 추출용 이미지도 35px 썸네일을 재사용해 추가 네트워크 비용이 생기지 않게 했다.

**결과 및 성과**
색상 관련 하드코딩 없이 모든 팀 화면에서 배경-텍스트 대비가 자동으로 확보됐고, 신규 팀이 추가돼도 프론트 작업이 필요 없는 구조가 됐다.

**회고**
YIQ 임계값 140은 경험적으로 잡은 숫자다. WCAG 대비비 기준으로 검증했다면 접근성 근거를 갖춘 값이 됐을 것이다. 또 추출 결과를 캐싱하지 않아 같은 팀에 재진입할 때마다 계산이 반복되는데, 팀 ID 기준으로 결과를 캐시했다면 불필요한 연산을 줄일 수 있었다.

### 회고 ④ 안드로이드에서는 되고 iOS에서는 깨지는 일정

**문제인식**
경기 일정 정렬이 iOS Safari에서만 깨졌다. 원인은 서버가 내려주는 `"YYYY-MM-DD HH:mm:ss UTC"` 문자열이 표준 포맷이 아니어서, 관대하게 파싱하는 브라우저에서는 통과하고 iOS Safari에서는 `Invalid Date`가 되는 것이었다. 정렬 키가 `NaN`이 되니 목록 순서 자체가 무너졌다.

**방안수립**
1. 서버 응답 포맷을 ISO 8601로 변경 요청
2. 클라이언트에서 문자열을 ISO 8601로 정규화한 뒤 파싱
3. 파싱 라이브러리에 커스텀 포맷을 지정해 위임

**방안선택 및 이유**
2를 선택했다. 1이 근본 해결이지만 이미 배치로 적재된 과거 데이터까지 소급해야 해서 수정 범위가 컸고, 3은 라이브러리 의존이 커진다. **파싱을 브라우저 구현에 맡기지 않는다**는 원칙을 세워 정규화 → `date-fns-tz` KST 변환을 공통 유틸로 묶었고, 잘못된 입력이 들어와도 화면이 죽지 않도록 방어 분기를 넣었다.

**결과 및 성과**
플랫폼별 날짜 파싱 편차가 사라져 일정 정렬과 표기가 전 환경에서 동일하게 동작한다. 날짜 처리 로직이 유틸 한 곳으로 모여, 이후 경기 상세·다가올 경기 화면에도 그대로 재사용됐다.

**회고**
데스크톱 크롬만 보고 "동작한다"고 판단했던 것이 원인이었다. 실기기 확인을 개발 흐름에 포함시켰어야 했고, 무엇보다 **서버-클라이언트 간 날짜 포맷을 계약으로 먼저 합의**했다면 애초에 생기지 않을 문제였다. 이 경험 이후 외부에서 들어오는 값은 경계에서 정규화한다는 습관이 생겼다.

### 회고 ⑤ 배포가 특정 로컬 환경에 묶여 있던 문제

**문제인식**
배포가 `빌드 → tar 압축 → scp 전송`의 수동 3단계였고, 개인 키 파일 경로가 npm 스크립트에 그대로 박혀 있었다. 다른 사람은 물론 다른 PC에서도 동일한 배포를 재현할 수 없고, 단계 중 하나만 빠뜨려도 실패를 늦게 알아채는 구조였다.

**방안수립**
1. 수동 절차를 문서화하고 셸 스크립트로 감싸기
2. GitHub Actions로 빌드까지 자동화하고 배포는 수동 유지
3. GitHub Actions + Docker로 빌드부터 이미지 배포까지 전 구간 자동화

**방안선택 및 이유**
3을 선택했다. 1·2는 "사람이 실수할 여지"와 "로컬 환경 의존"이라는 근본 원인을 남긴다. 컨테이너로 감싸면 노드 버전·OS 차이가 사라지고, 멀티 스테이지 빌드로 빌드 도구를 런타임 이미지에서 제외할 수 있다고 판단했다. 자격증명은 코드에서 걷어내고 GitHub Secrets로 옮겼다.

**결과 및 성과**
main 브랜치 push만으로 빌드 → 이미지 생성 → 레지스트리 푸시가 자동 수행되어, 사람이 개입하는 수동 단계가 3에서 0이 됐다. 배포 산출물이 이미지로 고정되면서 "내 PC에서는 되는데" 류의 환경 차이 이슈가 사라졌다.

**회고**
파이프라인을 세우는 과정에서 커밋을 여러 번 반복했는데, 이는 CI 설정을 로컬에서 미리 검증할 수단 없이 원격 실행 결과에만 의존했기 때문이다. `act` 같은 로컬 러너나 별도 검증 브랜치를 썼다면 시행착오를 압축할 수 있었다. 또 레지스트리 푸시 이후 서버 반영이 자동화되지 않아 파이프라인이 절반에서 끝나 있고, `latest` 태그만 사용해 롤백할 버전을 지목할 수 없다. 커밋 SHA 기반 태깅과 배포 단계 연결이 다음 개선 과제다.

## 5. 이 프로젝트에서 얻은 것

- **최적화는 축을 나눠서 접근한다** — 요청 시점(지연 로딩)과 요청 크기(썸네일)는 다른 문제이고, 하나만 해결하면 절반만 좋아진다.
- **상태는 성격에 따라 분리한다** — 서버 상태(React Query)와 UI 상태(MobX)를 섞지 않으니 화면이 늘어도 복잡도가 따라 늘지 않았다.
- **경계에서 정규화한다** — 외부에서 들어오는 값(날짜 문자열, 이미지 URL)은 진입 지점에서 형태를 통일해야 플랫폼 편차가 안쪽으로 번지지 않는다.
- **규칙으로 보장한다** — 색 대비를 눈으로 맞추는 대신 밝기 계산식으로 결정하니, 데이터가 늘어나도 품질이 유지됐다.
- **측정 없는 개선은 증명할 수 없다** — 가장 크게 남은 아쉬움이자, 이후 작업 방식을 바꾼 교훈.
